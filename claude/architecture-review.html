pmsim · architectural review · commit 4bba41f

Is this more complex than it needs to be?

Somewhat — but not because of the number of classes, and I'd argue against consolidation as the main lever. Half of the twenty-two classes are plain records with no behaviour. What makes the system hard to step through is that decisions are taken in places the loop never visits, a single setting crosses four layers to reach the one method that uses it, and the third of the code that is the model is not marked off from the two thirds that guard and report on it.

I wrote this code, so treat what follows as a second opinion from someone with an interest. I have tried to check each claim against the code or by experiment rather than from memory, and several of the findings are about decisions of mine that I now think were wrong.

One thing has changed since this was written. The review calls SizingBalances the wall that makes look-ahead impossible, and counts that as the design's best guarantee (§4, §5, §6 step D2, §7). You have since decided that a year drawn after a fund's closing must be priced on its own year-end value, with hindsight. The wall still stands for carry-forward; for draw plans there is now a deliberate, named door in it — SizingBalances.future_year_ends, read by one branch of drawn_years(), with every such row marked looks_ahead. The argument in §5 against folding the policy into the simulator is weaker for it, though I would still keep them apart: a door you can see is better than no wall. My read, in short

The class count is a symptom you can see, not the cause you feel. Merging classes would reduce the number of nouns and leave every one of the problems below in place — and two of the merges that look most natural would remove the clearest boundary the design has.

  • The loop is easy; what happened before the loop is not. By the time you step into Simulator.run(), which years each fund collects, how each fund's NAV evolves and what the portfolio is worth in dollars on every date have already been settled in constructors. The loop reads well because the thinking was done elsewhere.
  • A policy option is one idea and seven files. Rounding is about forty lines of logic. Adding it touched policy, spec, repository, orchestrator, simulator, __init__ and the script, and it has a different default at three of those layers.
  • The simulator and the policy are joined by one declared method and four undeclared ones. The simulator asks the policy the same question three times per closing, through getattr.
  • The model is 626 code lines of 1,866. Every assumption about private markets lives in roughly forty functions across ten files. Nothing tells you which forty.
  • Some of what is there is residue. Fields nobody reads, a stated reason for the step order that stopped being true three commits ago, generality your workbook never uses.

I also found two assumptions by experiment that I did not know the system was making (§7). One of them means that removing a single buyout fund from the Spec sheet changes every other fund's commitment by about 6%.

The dependency direction is sound

The import graph is acyclic and points one way: dates → timeline → inputs → state, policy → simulator, and data/ imports the core, never the reverse. benchmark imports nothing from the package at all. That is worth saying plainly, because it is the property that makes any of the changes discussed below cheap: nothing here is tangled.

Two small blemishes. inputs.py imports timeline, because Fund.align_history() returns an AlignedFundHistory — so the module described as “what the fund knows” also knows about the engine's grid. And data/tables.py and data/spec.py reach into policy.py for two validators, which is a leaf module depending on the heart of the engine for a four-line function.

3 · Where the difficulty actually comes from

Eight sources, roughly in order of how much I think each costs you at a breakpoint. Each is marked as inherent to the problem or incidental to how I structured the solution.

1

The decisions are made before the loop starts

mostly inherent

The design rule was “dates become periods, once”: everything dated is converted to arrays before run(), and the loop works on integers. It is why run() is 120 readable lines. The cost is that the loop consumes conclusions rather than reaching them:

  • commitment.nav_at(t) returns a number whose whole story — pooling, mark-replaces-NAV, the floor at zero — was written by inputs.py:132 during Simulator.__init__.
  • entitlement.draws arrives in policy.py:541 ready-made. Why SEC_VI collects 2010–2013 was settled by policy.py:335, inside a constructor, triggered by a lazy property.
  • liquid_only_usd[t] — the single number every commitment is sized on — is one line, simulator.py:245, and is complete for all 214 periods before period 0 runs.

I think this trade is right, and I would not undo it: the alternative is a loop that parses dates and walks event lists, which is how the original function you started from read. But it means the honest reading order is not “start at run()”. It is the four preparation functions first, then the loop. Nothing in the package tells you that.

2

Every sizing option is consumed in exactly one place, AnnualRatePolicy. To get there it is declared four times:

3

The simulator and the policy: one declared method, four side doors

incidental one latent crash

The design note says “policy is a plug”, and CommitmentPolicy declares a single method, size_commitments. What the simulator actually does:

# simulator.py
524   sized = self.policy.size_commitments(cohort, balances)          # the declared contract
359   expected_return = getattr(self.policy, "expected_return", None)  # side door 1
611   explain = getattr(self.policy, "explain_commitment", None)       # side door 2
631   drawn_years = getattr(self.policy, "drawn_years", None)          # side door 3
635   weight = self.policy.entitlements[fund.name].weight              # side door 4 — not guarded

Line 635 is a real defect: _draw_rows checks politely that the policy has drawn_years and then assumes it also has entitlements. A policy with one and not the other crashes mid-run. Nothing does that today — which is the point: the “plug” has exactly one shape that fits.

The second cost is at the breakpoint. For every fund at every closing, drawn_years() runs three times — once under size_commitments, once under explain_commitment, once under _draw_rows — each time recomputing the same plan dates, expected values and roundings. It is harmless for speed. But when you are stepping and land in policy.py:541 for the third time with the same fund, the natural thought is “why am I here again, and is it the same answer?” It is, but the structure gives you no way to know that.

4

The repository describes its data to a spec, which hands it to an orchestrator, which asks the repository

incidental partly bought by the database plan

WorkbookRepository knows its profile: it knows the liquid column is "EUR Moderate", that the FX column is EURUSD and quoted dollars-per-euro. Rather than hand over a liquid series and a dollar rate, it writes those facts into a SimulationSpec (repository.py:503), and the orchestrator then asks the same repository for a generic market_data table and looks the columns up by the names the repository just gave it (orchestrator.py:196). It is a round trip through a general-purpose interface.

The same shape repeats for the expected return, which is resolved twice by two different matching rules: by profile in repository.py:490, and by liquid series name in orchestrator.py:268. On the workbook path the second is never reached, because the spec always arrives with the first already filled in.

The reason is legitimate: you told me the data will come from a database, so the protocol is shaped like a source (tables of series) and not like the engine (a liquid path, a dollar rate). Whether that is right depends on something I can't see — see §10.

The guard rails are not waste. Your data arrives from a hand-edited workbook, and “row 47 of Flows has a blank Scale” is worth a great deal more than a KeyError four frames deep. That half is inherent to the job.

What is incidental is that the two halves are interleaved, so a reader hunting for assumptions must step through — or over — a validator for nearly every model line. Your stated goal is to understand every assumption and piece of logic. That is a goal about 626 lines. At the moment you have to read 1,866 to find them.

incidental

7

Residue from designs that have since changed

incidental

The system has been through several sizing rules in a few days — on the account, then in dollars, then on the liquid-only path. Each left something behind:

  • SizingBalances carries four members no production code reads: t, liquid_account_usd, private_nav_usd and total_usd. They date from when commitments were sized on the account. Only tests read them now. The loop still computes them (simulator.py:411) and a reader has to work out for themselves that they go nowhere.
  • The stated reason for the step order is no longer true. run()'s docstring says “commitments are sized before the cohort's own distributions arrive”. That mattered when sizing looked at the account balance. Sizing now looks only at liquid_only_usd and the year ends, which no flow ever touches — so step 4 could sit anywhere in the period and produce identical commitments. The order still matters for cash; it no longer matters for sizing, and the comment says it does.
  • Generality the workbook never uses. Long-format market data; long- and wide-format rate tables; Call and Distribution row kinds (your sheet writes only Flow and NAV); calls_are_negative=False; USDEUR-style columns; SheetLayout with non-default names. All exercised only by tests. Each is small; together they are a good part of why tables.py is 549 lines.
  • CommitmentBook.__len__ has no caller.
8

Assembly happens in an order nobody wrote down

incidental

Orchestrator has seven cached_property members. Calling .run() touches .simulator, which touches .portfolio, .funds and .policy, which touch .commitment_rates, .expected_return and .draw_plans — in whatever order Python evaluates the arguments. In the debugger that is a call stack that deepens sideways, and an error surfaces wherever the first touch happened to be. Your script works around it by touching funds, portfolio, policy in sequence on purpose (eur_moderate.py:105) — which is the script compensating for the class.

That is the pattern I'd draw your attention to. The nouns are mostly right. Some of the verbs are attached to the wrong noun.

5 · What consolidation would cost

Five merges that suggest themselves, and what each would do to a reader.

MergeEffect on comprehensionMy view
LiquidAccount → a float in run() Three fewer jumps per period. The loop shows liquid_pnl = balance × return where it happens. You lose named verbs; the step comments already supply them. Helps, mildly. The one merge I'd call a clear win.
SheetLayout → constants on the repository One fewer noun; nothing else changes.Helps, trivially.
Commitment + CommitmentBook You'd get one class that is both a thing and a collection of that thing. The per-fund rows in the funds table need the individual commitment.Hurts.
The four sizing records → fewer They are small because each is one idea: a year end, what the policy may see, what a fund is due, what a year came to. Merged, you get a wide record with fields that are meaningful only some of the time — which is harder to read at a breakpoint, not easier.Hurts.
AnnualRatePolicy → into Simulator The tempting one, since there is only one policy. Sizing would become linear in the debugger with no protocol and no getattr. But you would lose SizingBalances as a wall: inside the simulator, self._year_ends holds every year including future ones, and nothing but discipline would stop sizing code from reading it. Today the policy cannot look ahead, by construction.Hurts — it trades the design's best guarantee for convenience. Narrow the interface instead (§8).
Repository + Orchestrator + Spec One object that opens Excel, interprets sheets, holds settings, builds inputs and runs the engine. About 1,000 lines, and untestable without a workbook.Hurts badly. The problem here is the routing between the three, not that there are three.

Add it up and honest consolidation takes you from 22 classes to about 20. It would not touch findings 1, 2, 3, 4, 5, 6 or 8. That is the core of my disagreement with the instinct: the lever is small and it is attached to the wrong thing.

There is a version of the instinct I do agree with. It is not “fewer classes” but “fewer places”: fewer layers a setting passes through, fewer times a question is asked, fewer files that hold a piece of one idea. That is what §8 is about.

Three modelling assumptions sit in that chain that are easy to step past. A fund's own year is sized on the closing observation, while a carried year is sized on its year end — identical for your 31 December closings, different for a fund closing in June. A year after the closing is dated to 31 December of that year on the model's calendar, whatever the grid. And each year is rounded before its multiplier, so 12x3 is three rounded amounts, not one rounded total.

Two I found by experiment

The pacing clock belongs to the fund list. I removed one buyout fund, PEM2011 — the first to close — and re-ran. first_commitment_date moved from 31 Dec 2010 to 31 Dec 2011, and every other fund's commitment rose by a year's growth: SEC_VII from 3,810,000 to 4,040,000 (+6.0%), PEM2016 from 2,670,000 to 2,820,000 (+5.6%). The schedule is keyed to the inception year; its divisor is keyed to whichever fund happens to close first. They agree in your workbook. Nothing enforces that they do.

An overdraft is charged the portfolio's return. Described in D3 above. It only matters with stop_on_shortfall=False, but in that mode it is a financing assumption nobody chose.

8 · Alternatives to consolidation

Ways of attacking the actual sources. These are options with their costs, not a plan; several depend on §10.

Mark the model

Addresses
§3.5, §3.1
The idea
A reading map: the forty-odd functions that hold an assumption, in the order they execute, with the assumption each one makes. Section 6 above is a first draft of it. It could live as a document, or in the code as a consistent marker in those docstrings.
Buys
It shrinks what you must understand from 1,866 code lines to 626 without changing one. It is the only option here that addresses your stated goal directly.
Costs
It rots unless kept up. A marker in the code rots less than a document beside it.

Ask the policy once, and get the whole answer

Addresses
§3.3
The idea
One call per closing that returns, per fund, the dollars and the drawn years behind them. The simulator writes its commitment row and its draw rows from that one object.
Buys
Removes three getattr calls, the unguarded entitlements access, and two of the three computations. Stepping through a closing becomes one descent, not three. The protocol becomes honest.
Costs
A custom policy has to return the richer object, or a bare number gets wrapped for it. Small.

Give the sizing options one home

Addresses
§3.2 — the one I weight most
The idea
The six sizing options travel as one object from wherever they are chosen to the policy, instead of as six separate fields restated at each layer. One set of defaults, in one place.
Buys
The next option is a change to policy.py and that object. “Is rounding on?” has one answer.
Costs
It is a breaking change to SimulationSpec's shape and to your script. And it forces a decision I have been avoiding: what is the default for rounding and carry-forward? That is yours to make, not mine.

Assemble in a written order

Addresses
§3.8
The idea
Replace seven lazy properties with one routine of numbered steps — funds, rates, expected return, draw plans, portfolio, policy, simulator — in the style of run(), keeping each result inspectable.
Buys
The order is on the page. Errors surface at a predictable step. Your script stops needing to touch properties in sequence to get a sane debugging experience.
Costs
Assembly becomes eager: a bad Flows row fails construction rather than first use. I think that is better, but some tests rely on the lazy behaviour.

Shape the repository like the engine, not like the source

Addresses
§3.4
The idea
The repository hands over what the engine needs — a liquid return series in base currency, the price of a dollar, the schedule with its X, the funds — instead of generic tables plus a description of how to read them.
Buys
SimulationSpec loses about six fields; build_portfolio loses half its branches; the double lookup of X disappears; the round trip goes.
Costs
Each future source must do its own selection. Whether that is a cost or a benefit depends entirely on the database — §10. I would not do this before knowing.

Rename what means two things; delete what means nothing

Addresses
§3.6, §3.7
The idea
base_per_usd for the exchange rate; distinct names for stated and resolved draws; a word of yours for Entitlement. Remove the four dead members of SizingBalances, correct the run() docstring, drop __len__.
Buys
Cheap, and each one removes a small false trail.
Costs
Renaming the rate column changes your CSVs. Removing the dead fields closes a door for a policy that sizes on total wealth — which you told me you don't want, but it is your call.

Tie the pacing clock to the schedule

Addresses
§7, first finding
The idea
Define “the model is worth 1” by the schedule's own calendar — the end of relative year 1 — or state the seed date explicitly, instead of inferring it from whichever fund closes first.
Buys
Editing the fund list stops moving every commitment.
Costs
This is a modelling question before it is a code question, and you know the pacing model; I don't. It may be that “first commitment” is exactly what the model means, in which case the current behaviour is right and only needs saying out loud.

9 · Other architectural concerns

Things you didn't ask about that I think matter for how this evolves.

The result tables are the real interface, and they are held together by strings

benchmark.py, the examples, your CSVs and 272 tests all find things by column name. The rows are built as dictionaries in one place and the column lists are declared in another, and simulator.py:81 reconciles them silently: a key that is not in the declared list is dropped, and a declared column with no key becomes NaN. I checked. A typo in a row key produces a column of NaNs and no error. This is also why last week's rename of four columns rippled through thirty-four test lines.

Three front doors, three sets of defaults

Simulator(portfolio, funds), Orchestrator(FrameRepository(…), spec) and load_profile_workbook(…) build the same engine with different sizing behaviour (§3.2). The first is the most dangerous because it is the most convenient: examples/basic.py uses it, and it gives you a model in which the rate table means something different.

Model logic in an example

starting_balance() decides how a dollar starting value becomes euros. It is in eur_moderate.py:54. If that rule matters — and with START_IN_BASE_CURRENCY = False it sets the scale of the entire run — it belongs in the package, tested.

The simulator is half report writer

155 of Simulator's 364 code lines build rows. It is why the class is 732 lines, and it is why “step through the engine” means stepping past _fund_rows on every observation. The engine and its bookkeeping are separable, and the bookkeeping is the larger half.

The same small thing, written several times

“Is this a real, finite number and not a bool” appears in policy.py, spec.py and simulator.py. “Find the entry whose canonical name matches” appears four times across repository.py and orchestrator.py. The rate table is coerced and validated twice, once by Portfolio and again by the policy. None is a bug. Each is a place where a fix will one day be applied to one copy.

What is genuinely strong

I don't want the list above to mislead. The dependency graph is clean. The inputs are immutable. There is one loop, and one boundary where currency is applied. The look-ahead guarantee is structural and not a convention. And the tests are unusual in a good way: accounting identities are asserted on every run, and last week's restyling was verified by diffing 181 output tables at 17 significant digits. That last property is what makes everything in §8 safe to attempt. You can change structure here and know whether behaviour moved.

What I would not worry about

Performance. 214 observations, 19 funds, Python loops: the run takes a fraction of a second, and the triple pricing in §3.3 is a reading problem, not a speed problem. That changes completely if you ever want Monte Carlo over return paths — see below.

10 · What I can't see from the code

Five things that would change my answers. For each: what it decides.

QuestionIf yesIf no
Will there ever be a second sizing policy? A different pacing approach, a comparison run, a rule from another team. Keep the protocol, and make it honest: declare the richer return value (§8). Drop CommitmentPolicy. Call AnnualRatePolicy directly. Keep SizingBalances as the wall regardless.
What shape will the database deliver? Generic series tables, or portfolio-specific views? Generic tables: today's source-shaped protocol, and the long-format readers, are right and FrameRepository was worth building. Portfolio views: reshape the protocol around the engine; a good part of tables.py and SimulationSpec can go.
Does your real workbook use any of the unused generality? Long sheets, Call rows, USDEUR columns, renamed sheets. Keep those paths.They are a few hundred lines you never need to read.
Will anyone else read or change this? The reading map and the single home for settings matter more; conventions need writing down. Optimise purely for your own step-through. The spaced-out style and inspectable intermediates are already doing that.
Will you want many runs — scenarios, Monte Carlo, a sweep over X? The prepare-once design is exactly right and should be pushed further: most of Simulator.__init__ need not repeat per path. Row-dictionary reporting would become the bottleneck. Ignore performance entirely.

One more that is not a yes/no: what is chatgpt/ for? If you are comparing the two implementations to choose one, then the comparison that matters is not class count but how many places you have to look to answer “why is this commitment this number?”. In this package the answer is one table, result.draws. I would hold the other to the same test.

11 · If it were mine

You asked for thinking, not a plan. This is only where my own judgment lands, so you can argue with it.

I would not consolidate classes, beyond inlining LiquidAccount if stepping into it annoys you. I think the instinct is pointing at something real and naming it wrongly. What you are feeling is not that there are too many things; it is that to follow one idea — a setting, a commitment, an assumption — you have to visit too many places, and that nothing tells you which places matter.

So I would start with the thing that costs nothing and answers your actual goal: mark the model, and use §6 and §7 as its first draft. Walk it once in the debugger with SEC_VI. If, having done that, the system feels comprehensible, then the structure was adequate and the map was what was missing.

If it still feels like too much, the two structural changes I believe in are asking the policy once and giving the sizing options one home. The first makes a closing a single descent in the debugger. The second is what stops the next feature costing seven files — and it is the one I'd regret not doing if this keeps growing at the rate it has this week.

And separately from architecture altogether: decide what seeds the pacing clock. That one is not about comprehension. It is a number in your results that depends on something you would not expect it to depend on, and you should either choose it or fix it.
